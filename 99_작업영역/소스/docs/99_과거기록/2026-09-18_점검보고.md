# 저장소 검수 결과와 다음 실행 순서

검수 기준: `50bbcade9ca8b67a54139b1406fcee3a2fe997b4`. 검수 중 추가된 `7676292fe9ace5bcd777ba01d00b6a92ca2b12ca`까지의 문서 변경과 이전 작업자의 Windows 검증 기록을 보존했다. 이전 버전의 Windows 검증은 이번 수정의 Windows 검증으로 간주하지 않는다.

사용자 요청: 두 저장소를 읽고, 사용자 검수 없이 누적된 작업의 문제를 고친 뒤 다음 진행 방향을 판단한다.

## 판단

기능과 자동검사는 많이 있지만, 실제 사용 준비가 끝난 자동 게시 제품으로 판단할 근거는 부족하다. 우선순위는 수집량이나 플랫폼 수 확대가 아니라 **후보 하나를 실제 파일 제작, 검수, 복원까지 일관되게 처리하는 것**이다.

운영 허브는 문서·포인터 저장소이며 실행 앱이 아니다. Threads는 로컬 단일 운영자 도구다. 계정별 실험 메타데이터와 백업 범위가 있다는 사실은 계정별 인증·다중 사용자 접근 제어가 완성됐다는 뜻이 아니다.

코드·파일 이름과 기존 저장 키는 유지했다. 원본 이미지나 기존 게시물을 변경하지 않았다. 자동 개인정보 마스킹, 자동 승인, 실제 게시를 실행하지 않았다.

## 검증과 한계

- 변경 전 `npm run check` 통과. 따라서 기존 녹색 CI만으로 위 결함을 탐지할 수 없었다.
- 변경 후 Node.js 24.19.0에서 `npm run check` 전체 44개 테스트 통과. GitHub CI 결과는 PR에서 확인한다.
- 실제 HTTP 서버 테스트: 파일 경계, 잘못된 경로 후 서버 생존, Host/Origin, JSON 타입, 승인값, 8개 동시 저장 요청의 1개 성공/7개 409.
- 게시 중복 방지: 로컬 테스트 더블로 동시 요청, 재시작 후 응답 재사용, 응답 불명확 시 재시도 차단 확인. 실제 게시 API 검증이 아니다.
- Source Package: 실제 모델과 DOM 이벤트 핸들러를 연결해 완전한 입력, 후보 전환, 지연 이미지 응답, 실패 재생성, 비율 보존을 검사. 이미지 decode/canvas는 테스트 더블이다.
- 기존 영상 테스트는 실제 FFmpeg/ffprobe로 1080×1920 H.264 파일 생성/검증.
- 기존 6장 카드의 실제 PNG 크기와 계획 대비 SHA-256 재검증. 커버와 본문 표본도 시각적으로 확인. 전체 본문 누락/권리/사람 승인까지 검증했다는 의미는 아니다.
- 이 환경의 Cloud Browser는 로컬 앱 URL을 `ERR_BLOCKED_BY_CLIENT`로 차단했다. 실제 브라우저 조작·다운로드 완료·새 카드의 시각 검수는 미완료다.
- Windows 사용자 PC와 실제 계정의 인증/게시/Insights/수익은 이번에 검증하지 않았다.

## 남은 제품 작업

1. **실제 사용자 브라우저 검수.** 한 후보를 선택해 이미지와 전체 본문 확인을 입력하고, PNG를 받아 제목·본문 순서·읽기 크기·전체 파일 수를 확인한다. 다른 후보로 전환하고 돌아온 경우도 확인한다.
2. **복원 검수.** 상태 JSON과 원본 이미지를 각각 백업한다. 새 브라우저에서 상태 복원 후 이미지를 재선택해 같은 결과를 만들 수 있는지 확인한다. 원본 이미지가 서버에 자동 보관되는 것으로 표시하지 않는다.
3. **제작 경로 통합.** 새 Source Package는 메타데이터 저장과 PNG 출력까지 연결됐다. 기존 Card Factory canvas를 참조하는 04 공식 media staging과는 아직 별도 경로다. candidate ID, 자산 hash, 승인 버전을 가진 명시적 전달을 만들고 파일 검수 화면에서 확인해야 한다.
4. **한 계정 소량 운영.** 사용자가 최종 문안·이미지·계정을 확인한 뒤 실제 게시 성공 ID와 Insights를 기록한다. 그 전에는 자동 게시 운영 준비 완료로 부르지 않는다.
5. **성과 판단 후 확장.** 초기의 5개 표본 상대 점수는 통계적 성공 입증이나 수익 예측이 아니다. 실제 계정별 조회·참여·클릭 데이터를 확인한 다음 수집량, 계정 수, 플랫폼 수를 늘린다.

## 운영 한계

- API는 인증된 다중 사용자 서비스가 아니다. 로컬 사용이 전제다. 공개 reverse proxy가 필요하다면 `/media/staged/`의 검수된 자산 경로만 별도로 다루고 API 전체를 노출하지 않는다.
- JSON 쓰기 직렬화는 한 서버 프로세스 범위다. 여러 서버 프로세스가 같은 상태 파일을 공유해야 한다면 SQLite 백엔드를 사용한다.
- 게시 journal은 같은 provider/후보/승인/자격증명에 대한 중복을 막는다. 토큰 변경, 별도 서버 저장 경로, provider 간 중복까지 동일 계정으로 식별하는 시스템은 아니다.
- 응답 불명확 기록은 플랫폼에서 실제 게시 여부를 확인해 조정해야 한다. 기록 삭제나 새 승인을 만들어 무조건 재전송하지 않는다.
- 서버 백업은 수동 저장/복원이며 실시간 동기화가 아니다. 브라우저 저장공간과 실제 이미지 파일은 별도 관리가 필요하다.
